# GPT와의 대화..

이번에는 AWS에서 제창한 AIDLC에 대해 내용을 GPT에 물어보고 정리를 시킨 것이다. 다음은 그 첫번째.





## **1. AI-DLC가 등장한 배경**

기존 소프트웨어 개발에서는 AI를 주로 개별 작업에 활용했습니다.

예를 들어 GitHub Copilot이나 Codex를 사용해 코드를 작성하거나, 테스트 케이스를 만들고, 문서를 생성하는 방식입니다.

그러나 **코딩 속도가 빨라진다고 소프트웨어 개발 전체가 빨라지는 것은 아닙니다.**

개발 과정에는 여전히 요구사항 분석, 설계 검토, 업무 협의, 테스트, 배포 등 많은 활동이 존재합니다.

AI-DLC는 이러한 문제에서 출발합니다.



## **2. AI-DLC의 가장 중요한 원칙**

AWS의 원래 AI-DLC 설명은 두 가지 원칙을 강조합니다. 



**① AI-Powered Execution with Human Oversight**

AI가 계획을 작성하고, 필요한 정보를 질문하고, 승인된 작업을 실행합니다. 사람은 요구사항의 타당성, 설계의 적절성, 중요한 기술적 결정을 책임집니다.

**② Dynamic Team Collaboration**

개발자, 기획자, 아키텍트, QA 담당자가 AI와 함께 실시간으로 문제를 해결합니다. 문서를 주고받으며 장시간 대기하는 대신 짧고 집중적인 협업을 지향합니다.



## **3. AI-DLC의 3단계 개발 프로세스**

AWS가 처음 제시한 AI-DLC는 크게 세 단계로 구성됩니다. 

**1. Inception — 무엇을 만들 것인가?**

요구사항 분석, 사용자 스토리, 업무 범위 및 작업 단위 정의

**2. Construction — 어떻게 만들 것인가?**

아키텍처 설계, 도메인 모델링, 코드 생성, 테스트 및 검증

**3. Operations — 어떻게 운영할 것인가?**

배포, 인프라 관리, 모니터링, 운영 피드백

| 단계         | AI의 역할                           | 사람의 역할                      |
| ------------ | ----------------------------------- | -------------------------------- |
| Inception    | 요구사항 도출, 질문 생성, 작업 분해 | 요구사항 확인, 우선순위 결정     |
| Construction | 설계안, 코드, 테스트 생성           | 아키텍처 결정, 코드 및 품질 검증 |
| Operations   | 배포 구성, 로그 분석, 운영 지원     | 배포 승인, 장애 및 위험 판단     |

이 세 단계는 AI-DLC의 개념적 모델입니다. 실제 워크플로 구현에서는 프로젝트 규모와 변경 복잡도에 따라 세부 단계가 달라질 수 있습니다. 



## **4. AI-DLC에서 새롭게 사용하는 용어**

AI-DLC는 Agile의 일부 개념을 AI 중심 협업 방식에 맞게 재구성합니다.

| 용어               | 의미                                                         |
| ------------------ | ------------------------------------------------------------ |
| Intent             | 만들고자 하는 기능이나 비즈니스 목표                         |
| Unit of Work       | AI가 수행할 수 있도록 정의한 작업 단위                       |
| Bolt               | 수 시간에서 수일 정도의 짧은 개발 주기                       |
| Mob Elaboration    | AI와 팀이 함께 요구사항을 구체화하는 활동                    |
| Mob Construction   | AI와 팀이 함께 설계·구현·검증하는 활동                       |
| Persistent Context | 요구사항, 설계, 결정 사항 등의 맥락을 지속적으로 기록하고 활용하는 방식 |

특히 **Bolt**는 기존 Agile의 Sprint와 비교해 설명하기 좋은 개념입니다.

Sprint가 일반적으로 1~4주 단위라면, Bolt는 AI의 실행 속도를 활용해 수 시간에서 수일 단위로 작업을 진행하도록 제안합니다. 단, 이것은 방법론에서 지향하는 방식이지 모든 프로젝트가 그렇게 빨라진다는 보장은 아닙니다. 



## **5. 간단한 개발 사례**

예를 들어 부트캠프 교육생들이 온라인 도서 대출 시스템을 개발한다고 가정하겠습니다.

**Inception**

사람이 "사용자가 책을 검색하고 대출할 수 있는 시스템"이라는 목표를 제시합니다.

AI는 "동시에 같은 책을 대출하면?", "연체자는 대출할 수 있는가?", "최대 대출 수량은?" 등의 질문을 제안합니다.

팀이 답변하고 요구사항과 인수 조건을 확정합니다.

**Construction**

AI가 도메인 모델, API, 데이터 구조 및 테스트 코드를 제안하고 구현합니다.

개발자는 대출 규칙, 동시성 제어, 보안, 성능 등을 검토합니다.

자동화 테스트와 코드 리뷰를 거쳐 작업을 승인합니다.

**Operations**

AI가 Docker 구성, CI/CD 파이프라인, 배포 설정 및 모니터링 구성을 지원합니다.

개발팀이 실제 배포를 승인하고, 운영 중 발생한 문제를 다음 개발 작업에 반영합니다.

이렇게 AI-DLC에서는 각각의 개발 단계가 독립적으로 진행되는 것이 아니라 **이전 단계에서 검증된 산출물과 결정 사항이 다음 단계의 AI 작업 맥락으로 전달**됩니다.



## **6. AI-DLC와 관련 개념 비교**

| 구분                    | 핵심 관심사                                            |
| ----------------------- | ------------------------------------------------------ |
| SDLC                    | 소프트웨어 개발의 전체 생명주기                        |
| Agile                   | 반복적 개발과 변화에 대한 대응                         |
| TDD                     | 테스트를 먼저 작성하는 개발 방식                       |
| AI-Assisted Development | AI를 이용한 개별 개발 작업 지원                        |
| AI-DLC                  | AI와 사람이 **협업하도록** 개발 프로세스 전체를 재구성 |





## **7. AI-DLC의 기대 효과와 주의점**

**기대 효과**

요구사항 문서화와 반복적인 구현 작업의 부담을 줄이고, 설계·구현·테스트 사이의 맥락을 유지하며, 짧은 피드백 주기를 만들 수 있습니다.

**주의점**

잘못된 요구사항을 AI가 일관되게 구현할 위험, 생성 코드의 보안 취약점, 불충분한 테스트, AI 결과에 대한 과도한 신뢰 등의 문제가 있습니다.

따라서 AI-DLC를 적용한다고 품질이 자동으로 보장되는 것은 아닙니다. 오히려 요구사항 검토, 인수 기준, 테스트 전략, 보안 검토 및 추적 가능성을 명확히 해야 합니다.

특히 QA 관점에서 강조할 부분은 **AI가 만든 테스트가 통과했다는 사실과 시스템이 올바른 요구사항을 만족한다는 사실은 다르다**는 점입니다.
